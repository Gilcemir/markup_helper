# ADR-003: Dedicated IJatsInjector pipeline for XML post-processing

## Status

Accepted

## Date

2026-05-27

## Context

Phases 1/2 of DocFormatter are built on `IFormattingRule`, whose contract is
`Apply(WordprocessingDocument doc, FormattingContext ctx, IReport report)` —
each rule **mutates a `.docx` in place** via the OpenXml object model, wired
through `Microsoft.Extensions.DependencyInjection` and dispatched by a
subcommand (`phase2`).

Phase 3 is a different paradigm (see ADR-002): the `.docx` is a **read-only
source**, the **JATS XML is the mutation target**, an external `other.txt`
supplies one value, and some writes require **inline human confirmation**
(ADR-001). The existing `IFormattingRule` signature does not fit — its mutated
artifact is the wrong type and it has no notion of a paired source document, an
external lookup, or a confirmation gate.

The four tags are independent in placement but share one source-pairing and
reporting flow, which maps naturally onto a small set of ordered units.

## Decision

Add a **parallel Phase 3 pipeline** that mirrors the phase 1/2 structure but is
correctly typed for docx→XML injection:

- A new interface `IJatsInjector` with `void Apply(Phase3Context ctx, IReport report)`.
- A `Phase3Context` carrying the parsed read-only docx source, the target
  `XDocument`, the resolved `other` number, and an `IConfirmer` (ADR-006).
- Four injector implementations: `OtherIdInjector`, `EditedByInjector`,
  `DataAvailabilityInjector`, `CreditRolesInjector`.
- Registration via an `AddPhase3Injectors()` extension method, dispatched by a
  new `phase3` CLI subcommand, following the `AddPhase2Rules()` / `phase2`
  precedent.
- New code lives under `DocFormatter.Core/Jats/`.

## Alternatives Considered

### Alternative 1: Reuse `IFormattingRule`

- **Description**: Stuff the target `XDocument` into `FormattingContext` and
  implement the four tags as `IFormattingRule`s.
- **Pros**: Maximum apparent reuse; one rule abstraction across all phases.
- **Cons**: `Apply(WordprocessingDocument doc, …)` is the wrong shape — the
  docx is read-only here and the XML is the target; every Phase 3 rule would
  ignore its primary parameter and reach into context, an obviously leaky fit.
- **Why rejected**: Forces a semantically wrong contract onto Phase 3 for the
  sake of nominal reuse.

### Alternative 2: Single `Phase3Processor`, no abstraction

- **Description**: One class with four private injection methods called in
  sequence; no interface, no DI registration.
- **Pros**: Fewest types; strict YAGNI.
- **Cons**: Diverges from the established rule/pipeline/registration convention
  of phases 1/2; loses per-injector naming for the report and per-injector
  testability.
- **Why rejected**: The four tags are genuinely independent units; mirroring the
  existing convention costs little and keeps the codebase coherent.

## Consequences

### Positive

- Correct typing for the docx→XML paradigm; no leaky parameters.
- Consistent with phase 1/2 mental model (interface + DI + subcommand).
- Each injector is independently testable and individually named in the report.

### Negative

- A second pipeline abstraction exists alongside `IFormattingRule` (two ways to
  process a document in the codebase).

### Risks

- **Abstraction drift** between the two pipelines over time. Mitigation: keep
  `IJatsInjector` minimal and Phase 3–specific; do not attempt to unify with
  `IFormattingRule`.

## Implementation Notes

`FormattingPipeline`'s catch/log/rethrow-on-critical model is a good template
for a `Phase3Pipeline` runner. Reuse the existing `IReport` / `ReportWriter`
rather than inventing a new report type.
