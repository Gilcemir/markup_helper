# ADR-001: Ship the CBAB v26n3 CRediT corrections as one patch release across Phase 1 and Phase 3

## Status

Accepted

## Date

2026-09-14

## Context

Running `docformatter phase3` on the 15 articles of CBAB v26n3 produced 13
warnings or false negatives on the `credit-roles` rule. Diagnosis showed that
none of the 15 CREDIT statements is free prose: all are author-keyed, but the
authors use `;` where the parser only accepts `,` and `.`. Three further code
defects compound this: the docx reader silently discards a statement tagged
`[p]…[/p]`, the initials resolver is too permissive on given-name-only
candidates and too strict on hyphenated surnames and capitalized particles,
and the diagnostic JSON omits the statement text the operator needs.

Three articles also arrive with a broken `<surname>` (empty, or carrying the
ORCID). Investigation traced two of them to the Phase 1 header pipeline: a
plain-text ORCID inside the author name is not extracted and SciELO Markup's
`mark_authors` macro promotes it to surname; a name whose last token repeats an
earlier token ("Nguyen Hoai Nguyen") is mis-split by Markup's
`markup_surname_and_fname`, which tags the first occurrence.

The maintainer asked for these to be fixed together and released as a bug-fix
version (`v0.3.1`), with no priority ordering between the Phase 3 and Phase 1
blocks.

## Decision

Deliver the full correction set in a single release cycle, tagged `v0.3.1`:

- Phase 3: widen the author-keyed CREDIT grammar; stop the docx reader from
  swallowing `[p]` paragraphs; tier and broaden the initials resolver's
  candidates; add a `contrib-names` verification rule; carry the raw statement
  and per-author resolution status in the diagnostic JSON; aggregate CRediT
  pendencies and broken names in the batch summary.
- Phase 1: extract a plain-text ORCID out of the author name; warn when the
  last name token repeats an earlier token.
- Validate once against the v26n3 corpus (copied to a scratch location; the
  evidence folder is read-only) plus the existing Phase 2 diff gate.

## Alternatives Considered

### Alternative 1: Phase 3 now, Phase 1 in the next release

- **Description**: Ship only the Phase 3 corrections to unblock v26n3; defer
  the two `ExtractAuthorsRule` changes to `v0.3.2`.
- **Pros**: Smaller diff, faster release, fewer components touched at once.
- **Cons**: The next edition arrives with the same broken surnames and only
  the new WARN to catch them; two validation cycles instead of one.
- **Why rejected**: The maintainer explicitly asked for both blocks together
  and declined to prioritize; the Phase 1 changes are small and independently
  testable.

### Alternative 2: Minimal fix (parser and reader only)

- **Description**: Fix only the `;` grammar and the `[p]` swallow, which
  together clear 11 of the 15 articles.
- **Pros**: Lowest regression risk; touches two files.
- **Cons**: Leaves "SA" ambiguous, "LBB"/"TVB" unresolved, broken surnames
  invisible, and the diagnostic still without the statement text. Operator
  keeps reopening the docx to diagnose.
- **Why rejected**: The remaining defects are deterministic and already
  characterized; leaving them costs a second round on the same corpus.

## Consequences

### Positive

- One validation pass over v26n3 proves the whole set: 10 articles fully
  auto-applied, the other 5 pending only on docx defects, zero "free prose".
- The next edition is protected at both ends: Phase 1 stops producing the
  broken byline layout; Phase 3 flags whatever still slips through.

### Negative

- A larger patch release than the label "bug fix" usually implies; the
  `contrib-names` rule and the new diagnostic fields are new operator-visible
  behavior carried under a patch bump.

### Risks

- Regression in the Phase 2 diff gate (`examples/phase-2/{before,after}/`)
  from the `ExtractAuthorsRule` change. Mitigation: the gate stays part of the
  acceptance; any diff there blocks the release.
- Parser widening admits a shape that was previously (correctly) prose.
  Mitigation: existing prose fixtures stay as tests; the grammar still requires
  at least one mapped term and a `keys: terms` shape for every segment.

## Implementation Notes

Version is tag-based (`make release VERSION=v0.3.1` on `main`); release notes
are generated from commit messages, so commits should name the defect they
close. The technical grammar, resolver tiering and rule placement decisions are
recorded in the TechSpec ADRs, not here.
