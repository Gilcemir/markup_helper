# ADR-006: Confirmation gate via IConfirmer with an injectable non-interactive policy

## Status

Accepted

## Date

2026-05-27

## Context

ADR-001 requires an inline confirmation gate: ambiguous judgment calls pause for
human confirm/override before writing. But DocFormatter phases 1/2 are **fully
non-interactive**, and the golden-corpus tests invoke the CLI
(`CliApp.Run(["phase2", file], …)`) and diff produced output against expected
files. A blocking `Console.ReadLine()` prompt would hang those tests and any
unattended batch run. Phase 3 needs both interactive confirmation **and** a
deterministic non-interactive path.

## Decision

Introduce an `IConfirmer` abstraction with an injectable policy:

- `IConfirmer.Confirm(Proposal p) → ConfirmResult` returns the final value to
  write (the proposal as-is, or an operator override).
- `ConsoleConfirmer` prompts interactively — the default for the `phase3`
  subcommand.
- A `--non-interactive` CLI flag selects a non-prompting policy:
  - `accept` → `AutoAcceptConfirmer`: write the tool's best-guess proposal,
    recording it as auto-accepted in the report.
  - `fail` → `FailOnPromptConfirmer`: any attempt to prompt is an error
    (non-zero exit), surfacing newly-ambiguous documents.
- The injector is unaware of the policy; it always calls `IConfirmer.Confirm`.
  The policy is wired via DI per run, mirroring how phase 1/2 rules are
  registered.

The golden corpus runs with `--non-interactive=accept`, so expected XML encodes
the tool's proposals — the same test exercises the proposal logic. A separate CI
invocation with `--non-interactive=fail` asserts that no corpus document has
become ambiguous.

## Alternatives Considered

### Alternative 1: Golden corpus covers auto-cases only

- **Description**: Restrict the corpus to documents whose four tags are all
  high-confidence; cover proposal logic with isolated unit tests.
- **Pros**: Simplest corpus; no confirmer policy needed end-to-end.
- **Cons**: End-to-end coverage skips the prompt/proposal path entirely.
- **Why rejected**: The proposal path is where the risk lives; it deserves
  end-to-end coverage.

### Alternative 2: Scripted confirmer per test

- **Description**: Each test supplies a queue of canned confirm/override
  answers.
- **Pros**: Precise control over mixed auto+prompt scenarios.
- **Cons**: Every golden case maintains a brittle answer script beside its
  expected XML.
- **Why rejected**: Maintenance cost; `accept` policy plus a `fail` CI run gives
  most of the value without per-case scripts.

## Consequences

### Positive

- Interactive UX for operators; deterministic, hang-free tests and batch runs.
- The `fail` policy turns "a new document became ambiguous" into a loud CI
  signal.
- Confirmer is mockable, so injector logic is unit-testable in isolation.

### Negative

- `accept` mode can write a wrong proposal unattended — acceptable in tests
  (diffed against expected) but operators must not run `accept` blindly in
  production.

### Risks

- **Operators misuse `--non-interactive=accept` on real packages.**
  Mitigation: default the `phase3` subcommand to interactive `ConsoleConfirmer`;
  require the flag to be explicit; record every auto-accepted value in the
  report.

## Implementation Notes

`Proposal` carries the tag name, the proposed value, and a human-readable reason
for the prompt; `ConfirmResult` carries the final value and whether it was
accepted or overridden — both feed the per-file report so auto and confirmed
decisions are distinguishable (PRD auditability metric).
