# ADR-005: The CRediT outcome is recorded on Phase3Context and read by the diagnostic and the batch summary

## Status

Accepted

## Date

2026-09-14

## Context

The operator needs the raw statement, the recognized shape, and each author's
resolution status in `.diagnostic.json`, and a per-article pendency block in
`_batch_summary.txt`. `DiagnosticWriter.WritePhase3` today receives only the
XML, the report and the recorded dispositions; the CLI's `Phase3Outcome`
carries only processed/prompted/skipped/failed. The resolution is computed
once, inside `CreditRolesInjector.BuildPlan`.

## Decision

`CreditRolesInjector` writes a `CreditOutcome` record (raw, shape, entries
with author key, written terms, resolution status, unknown terms, applied
flag, and the document disposition) onto a settable `Phase3Context.Credit`
property at every exit of `Apply`, including the prose and header-empty
paths. `Phase3Processor` passes it to `DiagnosticWriter.WritePhase3` (new
parameter) and to `Phase3Outcome` for the batch summary. The diagnostic write
gate (WARN or above) is unchanged: "always" means whenever a diagnostic is
written. The broken-name count for the summary is derived from `contrib-names`
WARN entries in the report; no extra context field.

## Alternatives Considered

### Alternative 1: Recompute in DiagnosticWriter

- **Description**: the writer re-parses the raw text and re-resolves against
  the XML.
- **Pros**: no coupling to the injector.
- **Cons**: duplicated computation that can diverge from what was injected;
  the writer would need the confirmer's disposition anyway.
- **Why rejected**: two sources of truth for one outcome.

### Alternative 2: Structured payloads on IReport entries

- **Description**: report entries carry typed data next to the message.
- **Pros**: generic.
- **Cons**: changes the IReport contract for every rule in all phases for one
  consumer.
- **Why rejected**: disproportionate.

### Alternative 3: Write a diagnostic for every Phase 3 article

- **Description**: drop the WARN gate so clean articles get the CRediT block
  too.
- **Pros**: complete per-article audit trail.
- **Cons**: one more file per XML; changes existing DiagnosticWriterPhase3
  expectations; the `.report.txt` already lists injected roles.
- **Why rejected**: maintainer kept the gate.

## Consequences

### Positive

- One computation, three consumers (report, diagnostic, summary) agree by
  construction.

### Negative

- `Phase3Context` gains mutable state; only `CreditRolesInjector` writes it.

### Risks

- A future injector forgetting to record its outcome: not applicable, the
  record is CRediT-specific by design.

## Implementation Notes

`DiagnosticPhase3` gains a nullable `CreditStatement` property (serialized
camelCase by the existing options) rather than widening the shared
`DiagnosticPhase3Tag` record used by the other three tags.

Each entry carries `applied` (roles written in this run) and `alreadyPresent`
(skipped by the idempotency check because the `<contrib>` already had a
`<role>`). The distinction was added during the v26n3 acceptance run: a re-run
over an already-injected XML must read "already present", not "pending" —
those contributors are settled state, and the batch summary lists them apart.
