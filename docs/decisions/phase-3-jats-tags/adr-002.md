# ADR-002: Source values from the paired docx markup source, inject into the XML

## Status

Accepted

## Date

2026-05-27

## Context

Phase 3 must inject four tags into the JATS XML produced by SciELO Markup.
Inspection of the example corpus (`examples/phase-3/`) showed that the
generated XML **does not contain** three of the four values:

- The data-availability statement text, the CRediT statement, and the
  "Scientific Editor: \<name\>" line all live only in the **`scielo_markup/*.docx`**
  as *untagged* trailing sections — exactly the content the Markup tool drops.
- The XML carries the DOI, `<contrib>` authors, `<back>`/`<ack>`, and an
  `<author-notes>` containing only `<corresp>`.
- The `other` number is not derivable from any document; it is assigned
  externally by SciELO and provided in `other.txt`.

So the four values come from three places, and the XML alone is insufficient.

## Decision

Phase 3 takes a **paired docx + XML** per document and an external `other.txt`:

- **Value sources**: data-availability text, CRediT statement, and responsible
  editor (name + role) are read from the **docx markup source**; the `other`
  number is read from **`other.txt`**.
- **Injection target**: the **JATS XML** is the only artifact modified. The
  docx is read-only.
- Pairing of docx ↔ XML is per-document (the example corpus pairs by DOI; the
  docx's numeric id also appears embedded in the XML filename). `other.txt`
  is keyed by the package basename. The exact matching key is a TechSpec detail.

## Alternatives Considered

### Alternative 1: XML-only + external input files for everything non-derivable

- **Description**: Never read the docx; supply data-availability, CRediT, and
  editor via external files analogous to `other.txt`.
- **Pros**: Single uniform input mechanism; docx untouched.
- **Cons**: Forces manual transcription of document-specific content (the DA
  paragraph, per-author contributions) into external files — re-creating the
  MathML manual-entry friction this effort exists to remove.
- **Why rejected**: The values already exist in the docx; externalizing them is
  pure manual overhead.

### Alternative 2: Re-tag the docx (phase 2.5) and let Markup emit the XML

- **Description**: Instead of editing XML, mark the untagged sections in the
  docx with bracket tags so the Markup tool produces the final XML.
- **Pros**: Keeps a single XML producer (Markup); no direct XML editing.
- **Cons**: Depends on Markup supporting these tags (the premise of phase 3 is
  that it does not); moves the injection point and couples to Markup internals.
- **Why rejected**: User explicitly chose docx-source → XML-injection.

## Consequences

### Positive

- No manual transcription of content that already exists in the docx.
- Single, well-defined mutation target (the XML); docx stays untouched.

### Negative

- Phase 3 must parse untagged docx prose (no bracket tags around these
  sections), which is less structured than tagged content.
- Requires a reliable docx ↔ XML pairing key.

### Risks

- **Pairing mismatch** (wrong docx applied to an XML). Mitigation: pair by a
  strong key (DOI) and fail loudly on ambiguous/missing matches.
- **docx prose variation** across journals/authors. Mitigation: anchor on the
  section headers observed in the corpus (`DATA AVAILABILITY`,
  `CREDIT STATEMENT`, `Scientific Editor:`) and flag misses for confirmation.

## Implementation Notes

Placement rules per tag are already ported and documented in
`docs/scielo_context/jats/*.md` (validated against the old MathML project).
