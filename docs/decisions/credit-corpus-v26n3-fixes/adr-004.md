# ADR-004: Tiered, broadened candidate initials in the author resolver

## Status

Accepted

## Date

2026-09-14

## Context

`AuthorInitialsResolver.CandidateInitials` returns one flat set per
contributor: `given+surname+suffix`, `given+surname`, `surname+given`, and
`given` alone. Three v26n3 failures follow from it:

- 5524: "SA" matches Saleem Abid exactly (given+surname) but also Sajjad
  Ahmad Khan through the given-only candidate → `Ambiguous`.
- 5528: "Luis Barboza-Barquero" yields "LB"; the author wrote "LBB" →
  `NotFound`.
- 5613: "Truong Van Bui" yields "TB" because `Van` is dropped as a particle
  case-insensitively; the author wrote "TVB".

## Decision

- Candidates are built in two tiers. Tier 1 holds every full combination
  (given+surname+suffix, given+surname, surname+given). Tier 2 holds the
  given-names-only initials. A bare initials key is matched against Tier 1
  across all contributors; only when no contributor matches is Tier 2 used.
  Uniqueness is required within the tier that matched.
- Initials generation yields a set of variants per name part, not one string:
  a hyphenated token (`-`, `‐`, `–`) contributes both its first initial and
  the initials of each sub-token; a capitalized particle (`Van`, `Da`)
  contributes variants with and without it; a lowercase particle is dropped.
  Variants combine by cartesian product (bounded by the few tokens a name has).

## Alternatives Considered

### Alternative 1: Strict generation

- **Description**: two initials only for hyphenated surnames; only lowercase
  particles dropped.
- **Pros**: fewer candidates, simpler to document.
- **Cons**: an author writing "LB" or "MS" for "Maria Da Silva" falls to
  `NotFound` for no gain; uniqueness already protects against over-matching.
- **Why rejected**: the maintainer chose breadth; the tiering neutralizes the
  main ambiguity source.

### Alternative 2: Drop the given-only candidate entirely

- **Description**: remove Tier 2.
- **Pros**: eliminates the "SA" ambiguity class.
- **Cons**: 5316's authors resolve today only through it (full name kept in
  `<given-names>` because `<surname>` is broken).
- **Why rejected**: keeping it as a fallback tier costs nothing and preserves
  correct injections on defective bylines.

## Consequences

### Positive

- "SA", "LBB", "TVB" resolve; TTR/JGS/MRC still `NotFound` (their initials
  skip a name token, which no variant reproduces).

### Negative

- More candidates per contributor; ambiguity remains possible inside a tier
  and is still reported, never guessed.

### Risks

- Cartesian explosion on very long names: bounded by tokens × 2 variants for
  hyphen/particle tokens only; a name would need ~10 such tokens to matter.

## Implementation Notes

`ResolveBySurname` narrowing keeps using the union of both tiers. The
`Particles` set stays case-insensitive for lookup; the token's own casing
decides whether the "keep" variant is generated.
