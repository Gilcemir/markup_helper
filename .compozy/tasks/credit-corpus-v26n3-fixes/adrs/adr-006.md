# ADR-006: A plain-text ORCID in the byline is tokenized like a hyperlink ORCID

## Status

Accepted

## Date

2026-09-14

## Context

`ExtractAuthorsRule` extracts an ORCID only from a hyperlink target. When the
byline carries the identifier as plain text, it stays in the author's name
buffer; `RewriteHeaderMvpRule` then writes `Name 0000-…` followed by the
superscript label, and SciELO Markup's `mark_authors` takes the last
space-delimited token — the ORCID — as the surname. 5316 shows this on all
seven authors, glued to the surname on one of them (`Bruzi0000-…`). ORCID's own
display guidelines accept a plain URI, so this input is legitimate.

The same rule also cannot warn about a name whose last token repeats an
earlier one (`Nguyen Hoai Nguyen`); Markup's `markup_surname_and_fname` tags
the first occurrence and produces nested `[fname][surname]…` markup (5613).

## Decision

- `AppendRunTokens` scans non-superscript run text for an ORCID identifier
  (optionally prefixed by `https://orcid.org/`), with no word-boundary
  requirement before the digits so a glued `Bruzi0000-…` splits. The match is
  emitted as `TokenKind.Orcid` between the surrounding `Text` tokens, so the
  existing consume logic (flush the name, attach to the current builder)
  applies unchanged. An INFO line reports the extraction; if the builder
  already holds a different ORCID from a hyperlink, the builder gets a WARN.
- `FlagSuspicions` adds a WARN, without lowering confidence, when the folded
  last token of a name equals a folded earlier token.

## Alternatives Considered

### Alternative 1: Post-process the assembled name

- **Description**: after `EmitAuthors` builds the name, regex out the ORCID.
- **Pros**: fewer touch points.
- **Cons**: a second ORCID path; does not interact with separator handling
  (an ORCID sitting between two authors without a separator would attach to
  the wrong one).
- **Why rejected**: the token path already encodes the attach semantics.

### Alternative 2: Pre-mark `[surname]` in Phase 2 to bypass Markup's split

- **Description**: emit `[fname]`/`[surname]` ourselves.
- **Pros**: removes the dependency on `mark_authors`.
- **Cons**: violates the Phase 2 anti-duplication invariant (ADR-001 of
  phase-2-tagging-author-fixes; REENTRANCE.md).
- **Why rejected**: forbidden by an existing decision.

## Consequences

### Positive

- The next edition's bylines reach Markup with the ORCID after the label;
  the repeated-token case is announced before Markup mangles it.

### Negative

- The Phase 1 report gains lines on documents that were silent before.

### Risks

- A four-group number that is not an ORCID (unlikely in a byline) would be
  extracted; the INFO line makes it visible. The Phase 2 diff gate guards the
  curated corpus.

## Implementation Notes

`FormattingOptions.OrcidIdRegex` keeps its `\b` form for URLs; a second
generated regex without the leading boundary serves the plain-text scan.
