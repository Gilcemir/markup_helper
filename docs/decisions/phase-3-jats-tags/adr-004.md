# ADR-004: Pair docx ↔ XML ↔ other.txt on elocation-id, verify with DOI

## Status

Accepted

## Date

2026-05-27

## Context

ADR-002 settled that Phase 3 reads values from a paired `.docx` and injects into
the JATS XML, with `other.txt` supplying the `other` number — but explicitly
left the **matching key** to the TechSpec. Inspection of `examples/phase-3/`
shows the three inputs share **no common filename**:

- docx is named by a submission id (`5449.docx`).
- XML/PDF are named by the SciELO basename (`1984-7033-cbab-26-02-e54492621.xml`).
- `other.txt` keys on the PDF basename (`…e54492621.pdf\t00201`).

However, the docx `[doc]` header carries two strong keys that **do** match the
XML:

- `elocatid="e54492621"` → XML `<elocation-id>` and the XML/PDF/`other.txt`
  basename.
- `[doi]10.1590/1984-70332026v26n2a16[/doi]` → XML `<article-id pub-id-type="doi">`.

So a robust pairing exists, and two independent keys are available to
cross-check it.

## Decision

Pair on **elocation-id as the primary key, with DOI as a verification key**:

- Extract `elocatid` from the docx `[doc]` header; match it to the XML
  `<elocation-id>` (and to the XML/PDF basename used by `other.txt`).
- Independently extract the DOI from the docx (`[doi]…[/doi]`) and from the XML
  (`<article-id pub-id-type="doi">`); assert they are equal.
- **Fail loudly** (skip the document, non-zero outcome, report the reason) if
  the elocation-id is missing on either side, if no `other.txt` entry exists, or
  if the two DOIs disagree. Never proceed on a half-matched pair.

## Alternatives Considered

### Alternative 1: DOI only

- **Description**: Pair purely on DOI (docx `[doi]` ↔ XML `article-id`).
- **Pros**: A single globally-unique key.
- **Cons**: No second key to catch a bad match; `other.txt` is still keyed by
  the elocation-id basename, so that key must be read anyway.
- **Why rejected**: Loses the free cross-check; ignores the key that already
  unifies all three inputs.

### Alternative 2: elocation-id only

- **Description**: Pair purely on the elocation-id basename across all three.
- **Pros**: Simplest; one key everywhere.
- **Cons**: A single key with no corroboration; a transposed/duplicated
  elocation-id would silently mis-pair.
- **Why rejected**: The DOI cross-check is cheap insurance against exactly the
  failure mode (wrong docx applied to an XML) flagged as a top risk.

## Consequences

### Positive

- Two independent keys agree before any mutation — strong protection against
  applying the wrong source.
- The elocation-id is also the `other.txt` lookup key, so one key drives all
  three inputs.

### Negative

- Requires parsing the docx `[doc]` header (a small bracket-tag parse) in
  addition to the trailing prose sections.

### Risks

- **A document legitimately lacks an elocation-id or DOI.** Mitigation: fail
  loudly and report; do not guess a pairing.

## Implementation Notes

The `[doc …]` header is a single bracket tag near the top of the docx; extract
`elocatid` and the following `[doi]…[/doi]` with a focused parse rather than a
full bracket-tag interpreter. `other.txt` is a TSV; key on the basename minus
extension.
